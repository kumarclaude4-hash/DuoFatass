# RISK REGISTER

Tracks residual risk for every finding that ends as `accepted` or
`deferred-with-justification`, plus program-level risks. Findings ending as
`fixed` are recorded in FINDING_INDEX/MASTER_CHECKLIST and need no entry here
unless residual risk remains.

Policy: Critical/High findings may only be `fixed` or `accepted-with-justification`
(never deferred). Medium/Low/Informational may be fixed, accepted, or deferred.

| S03-H1 | High | fixed (R2) | **The server-side fix converts a confidentiality breach into an availability DoS, but the shipped rules change largely removes the precondition.** `/mediaToken` fails closed when a scopeId resolves to both a chat and a group. **Corrected 2026-08-10 (S02b):** an earlier draft of this row and of `sessions/SESSION-02.md` stated `firestore.rules` was left untouched and that squatting was therefore still freely possible. That is **wrong** — `bb5b8bb` did harden `groups` create with `!exists(chats/$(groupId))` + `createdBy == request.auth.uid` + `createdBy in members`, so an attacker can no longer create a shadow group over an **existing** chat at all. Residual DoS is now narrowed to a **race/ordering window**: a group created *before* the colliding 1:1 chat exists (the `exists()` check cannot see a future document), which would then deny both real participants that conversation's media. Requires pre-computing a chatId for two users who have never yet opened a chat. No data is exposed. **This residual is UNVERIFIED** — the rule is source-reviewed only; the regression tests that would prove it were never executed (emulator BLOCKED, no JVM). | Deliberate trade: denying a real participant costs availability, allowing the attacker costs confidentiality of another user's media. Fail-closed is correct at this layer and the ambiguity is unforgeable evidence of tampering, so it is logged at `warn` as an active-attack signal. The two layers are complementary and both are wanted: the rule prevents the collision, the server contains it if one is ever reached. The remaining namespacing work (group IDs are still client-chosen) stays owned by **S01-L1**, now `partial`, scheduled R3. | (1) **Run the 4 `S03-H1` tests in `firestore-tests/rules.test.js` against the emulator in CI** — this is the top outstanding action for this row and the only thing that would move it from source-reviewed to verified. (2) Close the availability residual when S01-L1 lands server-generated/namespaced group IDs, which removes the create-before-chat window entirely. (3) Revisit if a `warn`-level `scope-ambiguous` log is ever observed in production — that is an attack in progress, not noise. |
| S06-H3 | High | fixed (R2) | Two residuals. (1) **Single load-bearing call site:** the offline duress lock works only because `BaseActivity.onStart()` calls `maintainLockCredential()`. This method previously had *zero* callers and the failure was completely silent — no crash, no log, no test — so a future refactor can silently re-break it. (2) **First-run / never-online-since-install window:** if a duress code is triggered before any warm nonce has ever been parked, no credential exists, the intent cannot be drained, and the account stays unlocked; the code records this and logs `account believed UNLOCKED` rather than pretending success. | (1) Cannot be closed by an assertion in code — an Android instrumentation test is required, and there is no JDK/Android SDK in this environment (BLOCKED), so it is documented in-code as load-bearing instead of being test-enforced. (2) Inherent: `/duress-lock` authenticates with the nonce itself and `/requestLockNonce` needs the Firebase session that the wipe destroys, so a process that never obtained a nonce can never obtain one for that uid again. Preserving the honest "believed unlocked" record (S06-L4/S06-I2) is the compensating control. | (1) Add an instrumentation/Robolectric test asserting a warm nonce is parked after a foreground start, as soon as an Android build environment exists — this is the intended permanent fix. (2) Revisit if a server-side push-initiated lock (not dependent on a client-held nonce) is introduced, which would remove the window entirely. |

| S04-H1 | High | fixed (R2) | **DNS rebinding survives.** `resolveAndCheckHost()` is a check-then-connect sequence: it resolves the name, refuses any non-public address, and then `fetch()` resolves **again** independently. An attacker controlling authoritative DNS with a sub-second TTL can answer the first lookup with a public address and the second with `169.254.169.254` or `10.x`. The window is narrow and requires an active, well-timed race against a specific request, but it is real and it is not closed by anything in this fix. Also inherent: the guard blocks by address class, so a legitimately public host that itself proxies to an internal service is indistinguishable from any other public host. | Accepted for this round as a deliberate scope decision, not an oversight. Fully closing rebinding requires pinning the socket to the already-validated address (a custom `lookup`/agent hook on the fetch), which is a larger change to the request path than cluster B's budget allowed and carries its own regression risk on redirects. The fix still moves the finding from **permanently open to any attacker with a DNS record** — the state the audit found, where `internal.example.com → 10.0.0.5` simply walked through a hostname-string check — to **requires winning a timing race**. The limitation is stated in `egressGuard.js`'s own docblock so the next reader cannot mistake the guard for complete. | Implement address-pinned fetching (validate once, connect to that exact IP) when the request path is next touched. Revisit immediately if any endpoint other than `/linkPreview` and `/linkPreviewImage` begins fetching user-supplied URLs — grep for new `fetch(` call sites taking client input, since the guard protects only the callers that invoke it. |
| S05-H1 | High | fixed+runbook (R2) | **The admin surface remains a single static bearer token with no expiry and no per-operator identity.** The entropy gate guarantees the token is unguessable; it does nothing about a token that leaks. There is no rotation schedule, no revocation short of a redeploy, and every audit row attributes actions to "whoever held `ADMIN_TOKEN`" rather than to a person. The brute-force ceiling is in-memory and per-process, so it is also per-instance (see `S04-L3`/`S02-I2`) and IP-keyed, which `S04-M1` shows an IPv6 /64 defeats. | Accepted for this round. Real operator identity means SSO or per-admin credentials, which is a product decision and a much larger change than the finding asks for; the finding's own scope is the entropy floor, startup validation and the failure ceiling, all of which shipped. Rotation is an operator action that this environment cannot perform (no console access) and is tracked in `migration/MIGRATION_PLAN.md` rather than re-attempted by AI sessions per protocol §6. Compensating control: durable `admin_login_*` audit rows (`S05-H3`) make a leaked-token session *detectable after the fact*, which it previously was not. | Rotate on any suspicion of exposure. Revisit the identity question if a second operator is ever added — the moment "who did this" has more than one possible answer, the shared token stops being adequate. Re-check the lockout keying when `S04-M1` (IPv6 /64) is fixed in R3. |
| S05-H3 | High | fixed (R2) | **Two residuals.** (1) **The audit write is fire-and-forget** — a failed Firestore write is logged to the console and otherwise dropped, so an attacker who can reliably break that write (quota exhaustion, sustained outage) can act with reduced traceability. (2) **Verification is structural, not behavioural**: `adminAuditWiring.test.js` proves the call sites exist, and the Firestore rule is source-reviewed, but nothing in this environment proves a row actually lands in `adminAuditLog` — no emulator, no service-account credentials. | (1) Deliberate: an audit sink that can block or fail a login turns a logging dependency into an availability dependency for the admin panel, which trades a real outage for a marginal integrity gain. The failed write is itself logged. (2) Honest limitation of the environment, stated in the test file's own header instead of implied away — this is the `PR-4` toolchain gap, and the structural test is the strongest check available without provisioning a toolchain the protocol warns against provisioning for low-value checks. | (1) Revisit if durable audit becomes a compliance requirement, at which point the write should become awaited-and-alerting rather than fire-and-forget. (2) Replay a real `POST /admin/login` against the Firestore emulator and assert the resulting row when the `PR-4` CI exists — same gate as the unexecuted rules tests. |
